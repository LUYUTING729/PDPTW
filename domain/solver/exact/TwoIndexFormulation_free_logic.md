# `TwoIndexFormulation` 中的"放飞"逻辑（free node / free route）

这份说明面向第一次阅读代码的同学，用中文梳理 `TwoIndexFormulation.cpp` 里和 `freeNodes`、`freeNodesNum`、`freeRouteIndices` 相关的暖启动（warm start）流程：它想解决什么问题，具体怎么做。

## 1. 背景：为什么要“放飞”节点或整条线路？
- 求解器通常会把已有可行解作为暖启动，尽量沿用现有线路，减少求解时间。
- 但有时我们想“拆掉”一部分点或路线，让求解器重新规划。例如：
  - 只释放若干取送对，看看能否插入得更优（`freeNodes=true`）。
  - 只固定部分车辆线路，让剩余线路自由调整（`freeNodes=false` + `freeRouteIndices`）。
- “放飞”= 不把对应弧/变量钉死为 1，而是仅提供 start 值，留出改动空间。

## 2. 术语对照（方便看代码）
- **原始节点编号**：输入实例里的编号。
- **新节点编号**：Gurobi 模型内部用的连续编号。规则：
  - 取件 1..pickupCount，送达 pickupCount+1..2*pickupCount。
  - 仓库节点：0 和 `totalNodeNumInGraph-1`。
- **free node**：被刻意移出当前解的取送对。
- **free route**：整条车辆线路允许求解器重排。

## 3. 共同的暖启动铺垫（两种模式都要做）
1. 先把所有弧的 start 设为 0，避免遗留值污染。
2. 遍历现有解的每条线路，按行驶顺序累计：
   - `x[i][j]` 的 start：按照线路顺序依次设 1。
   - 服务开始时间 `b`：累计行驶时间 + 服务时间。
   - 载重 `q`：累计需求变化。
   - “路线标识”变量：把节点和它所在线路的首节点绑定，便于后续路由约束。
3. 记录各线路的最晚回仓时间，最终把“终点仓库”变量初始化为该最大值；仓库的 `q` 仍为 0。

## 4. 只放飞指定节点（`freeNodes=true`）时的额外处理
1. 复制当前解，重复调用 `stringRemoval`，直到有 `freeNodesNum/2` 对取送点被移出。这样得到“未固定”的节点集合。
2. 用原始→新编号映射填充 `nodeFreeFlags`，标出哪些节点被放飞。
3. 重新遍历每条线路并设置弧：
   - 若弧两端 **都不是** 放飞节点，则把该弧下界设为 1（相当于固定为已走）。
   - 只要弧连接到放飞节点，就 **不** 固定下界，仅保留 start 值，方便求解器重新插入。
4. 时间和载重的初始化仍按铺垫步骤进行，仓库时间取各线路最晚回仓时间。

**核心效果**：大部分线路保持不变，只留出若干取送对让模型自行寻找更好的插入位置。

## 5. 只放飞整条线路（`freeNodes=false`）时的额外处理
1. 根据 `freeRouteIndices` 生成 `routeFreeFlags`，标记哪些车辆线路可调整。
2. 对每条线路：
   - 先按铺垫步骤写入 start 值。
   - 如果该线路 **不允许** 放飞：
     - 经过的弧全部下界设为 1。
     - 时间 `b`、载重 `q`、路线标识变量都设定为“上下界相同”的固定值，彻底锁死该线路。
   - 如果该线路被放飞：只保留 start 值，不设下界或相等的上界，求解器可自由重排。
3. 仓库时间同样取所有线路的最晚回仓时间，仓库载重仍为 0。

**核心效果**：部分车辆路线完全锁定，剩余车辆可自由重排，兼顾稳定性与改进空间。

## 6. 小结
- 暖启动通过“start 值 + 选择性固定”来平衡**求解稳定性**和**改进空间**。
- 放飞的节点/线路保留原有起点提示，但不强制走同样的弧；固定部分则用弧下界和相等的上下界锁住。
- 这样 Gurobi 能在不推翻全部解的情况下，针对指定范围做局部优化。
